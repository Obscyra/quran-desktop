# Quran for Desktop — project memory

Free, open-source (GPL-3.0), ad-free desktop Quran app for Windows and macOS, with Linux builds (AppImage, deb, rpm) from CI. The owner checked the macOS and Linux builds on real machines: they work.
Tauri 2 + SvelteKit (adapter-static, ssr=false) + Svelte 5 runes + TypeScript. Repo:
https://github.com/Obscyra/quran-desktop (branch `main`, public). Inspired by
https://github.com/quran/quran_android (credit it and keep its Android links in the README; the app now has its own icon).
Data from the Quran.com public API v4. App code is in `app/`; `reference/` (gitignored) holds a clone
of quran_android.

## Architecture (app/src/lib)
- `api.ts` quran.com calls: `fetchVerses` (words with `code_v2` glyph, `v2_page`, tajweed markup,
  audio_url), `fetchIndo` (IndoPak text + 15-line layout via `mushaf=3`), `fetchChapterAudio`
  (per-word segments), reciters, translations.
- `fonts.svelte.ts` loads quran.com page fonts `verses.quran.foundation/fonts/quran/hafs/v2/woff2/p{n}.woff2`
  as `QCF{n}`, cached in IndexedDB (`offline.ts`, DB v3: text, audio, blobs, fonts, indo).
  `has()` must read `tick` to stay reactive.
- `player.svelte.ts` audio engine: lazy audio load (`prepareAudio`), `playVerse` (range + loop),
  `playFrom`, `playWord` (wbw mp3, or segment offline), `goTo`/`jump` for bookmarks and search.
- `reader.svelte.ts` page state incl. two-page spread (even page right, the next odd page left: 2 faces 3). `pages.ts` groups
  words by page/line (normalises by reading order; the API mislabels some verses).
- `settings.svelte.ts` (localStorage `quran.settings.v2`), `bookmarks.svelte.ts`, `ui.svelte.ts`,
  `actions.ts`, `translations.svelte.ts`, `updater.svelte.ts`, `themes.ts`, `platform.ts`.
- Components: `TitleBar` (custom chrome; Verse by Verse | Reading switch; listen/focus/fullscreen/menu),
  `Reader` (sub-bar + modes), `PageSheet` (one Mushaf page; `fit()` sizes text to the widest line),
  `Word`, `End` (verse-end marker), `WordMenu`, `Sidebar` (Surahs | Bookmarks, type `55:13`),
  `PlayerBar`, `Settings`.
- Gotchas: `text-rendering: geometricPrecision` on glyph text (hinting draws stray strokes otherwise);
  word padding in `em` so line fitting scales linearly; `$state.snapshot()` before storing proxies in
  IndexedDB; never `pkill -f "vite dev"` (kills the shell) — use `fuser -k 1420/tcp`.
- Listen-only reciters: `reciters-qa.ts` (92 whole-surah recitations of quranicaudio.com, ids 10000+, generated by `scripts/update-reciters.mjs`; its list API has no CORS so it ships as a file). They have no timings (`ChapterAudio.plain`): no highlight, verse stepping or play-from-verse; the picker groups them under "Listen only" below "Follow along".
- Reciters: `reciters.ts` is quran.com's list with portrait paths (`static.qurancdn.com/<photo>`); recordings
  without word timings (`approx`) get word timings estimated from verse spans in `player.fetchAudio`.
- Reminders / verse of the day: `notifications.svelte.ts` + `NoticeCard.svelte`; system toasts use
  `tauri-plugin-notification` (Cargo + capability added, not yet compiled on Windows).
- Smoothness rules (measured with the CPU throttled 4x, see git log): layout changes (sidebar, player bar) are
  one reflow plus a transform glide, never an animated width/height; the paged reader keeps the current spread and
  its neighbours mounted (neighbours hidden, laid out when idle); long surahs render in batches (`upto` in
  `Reader.svelte`); the sweep layers are made by `sweep.ts`; Settings is an overlay over a mounted reader.
- Left-click a word plays it; right-click opens `WordMenu`. Back/forward trail lives in `player.svelte.ts`.
- Fonts bundled in `app/static/fonts`: KFGQPC Uthmanic Hafs, IndoPak Nastaleeq (from quran.com), Inter, and
  `arabic/` (Amiri Quran, Noto Naskh Arabic, Scheherazade New, OFL): Windows has none of the three.
- Tray and background (`src-tauri/src/lib.rs`): tray icon (Open / Quit), `tauri-plugin-window-state` (size, position, maximized;
  not VISIBLE, so a window hidden in the tray never makes the next launch start hidden), `tauri-plugin-autostart` (starts with
  `--hidden`). Closing the window hides it when `settings.background` is on: done in the JS `onCloseRequested` in `+page.svelte`
  (a Rust close handler would be undone by that listener). A pending update still installs on close.
- `PageSheet.fit()` divides measured widths by the page's own transform scale (`k`), so it is right even during a glide;
  the Reader glide skips a page that was hidden (zero size). Tajweed class names contain hyphens (`custom-alef-maksora`).
- Single instance: `tauri-plugin-single-instance` must be the first plugin (a second launch shows the running window). Window size is saved
  400 ms after the last resize/move by `remember_window` in `lib.rs` (the plugin alone only saves on exit, rare for a tray app).
- Scroll views: `settings.lockPlaying` + `centerPlaying`/`playingBounds` in `Reader.svelte` (verse centred whole; taller verses follow the word);
  unlocked, a `.back` arrow shows when the verse is off screen. Rects are divided by `k` (interface zoom).
- Window fit (`+page.svelte`): `fit()`/`refit()` write the real `window.innerHeight` to `--vh` (used by `.app` height) and reset the scroll on resize, focus, scroll and visibilitychange. A window hidden in the tray can come back with a stale 100vh and a scrolled page (top bar and player lost); this fixes it. Check it on real Windows, not in a browser.
- Continue where I left off (`player.svelte.ts`): the verse is saved in `quran.verse`, and how far the recitation got in `quran.time` (every 2 s while playing and on pause; cleared when the surah ends or another opens). On launch `restoreTime()` fetches the audio, seeks, opens the player bar and stays paused. Skipped when offline and not downloaded, or when the app was opened on a `#/surah` link.
- Zoom speed: `.verse` uses `content-visibility: auto` (a text-size change only lays out what is in view); `PageSheet.fit()` keeps a `scaled` map (text size as a fraction of page width) so a page zoom does not measure every word again. The Verse by Verse zoom buttons show the text size as a percentage of 56 px; `Tooltip.svelte` follows a changed `title` with a MutationObserver.
- Scroll reading mode (`Reader.svelte` `watchPage`, `PageSheet` `stagger`/`live`; `.pg` has `content-visibility: auto`, which halved the long tasks at 4x CPU because off-screen pages are not laid out or painted; a page built ahead is fitted as soon as the browser is idle, so it is finished before it scrolls in, and the nearest page is built first): a page in view is built at once, pages within ~14000 px (about 12 pages, roughly +1.2 MB of heap each) are built ahead one per idle slot, and one is dropped only beyond ~30000 px; a page built while scrolling is drawn 4 lines per frame and its fit is measured only once it is on screen or the browser is idle. At 4x CPU throttle the longest task while scrolling fell from ~530 ms to ~200 ms.
- Shipped page sizes (`src/lib/fit-data.json`, made by `scripts/learn-fit.mjs`, about 40 KB, committed): the text size of every Mushaf page (standard layout, page fonts) measured once in the app itself, keyed `chapter:page:lines:words`. `PageSheet.fit()` uses it with one check of the widest line instead of measuring every word (text widths are not exactly linear in size on every machine). Run the script again (dev server up, `playwright` package; about 20 minutes) if the page fonts, the page layout or the word spacing CSS change; a page not in the file is simply measured. A wrong file shows as lines overflowing, so check with a scroll test.
- Testing in the real Windows window (`scripts/win-test.mjs`): the owner's installed app must be closed (single instance would take the launch over). Run `Quran.exe` with `WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9333` and `WEBVIEW2_USER_DATA_FOLDER` set to a scratch folder (the owner's data stays untouched), then connect with `playwright-core` `connectOverCDP` from Windows node (`C:\Users\magnum\quran-pw`, `npm i playwright-core`; run with `node.exe` through powershell). It reports long tasks, heap, this app's memory and CSP violations. Measured on this machine, scrolling Al-Baqarah at 17,500 px/s: long tasks 2.7 s (worst 455 ms) before the shipped sizes and wider cache, 1.2–1.6 s (worst 150 ms) after; at normal wheel speed 0 to 1 long task. A local build with the faster profile took 2 min 19 s once dependencies were built (6 min 22 s for the first one).
- Feature hints (`hints.svelte.ts`, `HintCard.svelte`): behaviour counters (`hints.note('barPeek' | 'backArrow' | 'zoom')`, called from `PlayerBar` and `Reader`) earn a small card offering the matching setting as a switch (floating player, lock on the playing verse, Fill). Rules: one hint per session and per 20 h, at most twice per hint, never when the setting was already changed, waits while the welcome, Settings or a notice is showing (retries every 4 s). Settings → App & window → "Show tips" (`settings.tips`, on by default; `hints.enable()`) switches them all off, and switching on again resets the history. Counters and dismissals live in localStorage `quran.hints`, nothing leaves the device. Add a hint by adding an entry to `HINTS` and a `note()` call. Page-turning tips (`reader.go()` notes `pageTurn`): two pages side by side (6 turns), translation (10, a link to Settings), scroll instead of pages (14), zoom and Fit/Fill (20). Counts are totals and each hint keeps `at`, the count when it was shown, so they arrive one at a time, 20 h apart. A hint with no `label` has no switch; `link` renames the Settings button.
- Buttons share one look (tokens in `app.css`: `--btn`, `--btn-hover`, `--btn-line`, `--btn-on`): a soft fill with no outline; the chosen one of a group (`.seg`) and an on/off icon (`.on`) are an accent tint with accent text. Only the main action (Play, Next, Listen) is a solid accent block. Use the tokens for any new button instead of a one-off tint. The player bar floats as a rounded blurred card in hover mode, with a knob on the seek bar and a styled volume slider. Welcome's language step is a searchable language list beside the translation list (no native selects).
- Controls outside the window (`src-tauri/src/media.rs`): Windows gets Previous / Play-Pause / Next buttons under the taskbar thumbnail (ITaskbarList3 thumb bar, icons drawn in code, window subclass on the main HWND, re-checked every 3 s because the shell drops them; problems are logged to `%TEMP%\quran-taskbar.log`); macOS and Linux use `souvlaki` (Now Playing / MPRIS) on its own thread, which has never been compiled or run on those systems (CI is the first build). The page reports state with the `media_state` command (`+page.svelte`) and handles the `media-control` event (prev, next, play, pause, toggle). `Cargo.lock` is now committed: without it CI took a newer `tauri-plugin-notification` than the npm package and the build refused the mismatch, so keep the npm and crate versions of Tauri plugins in step.
- Window frame: Windows draws its own title bar and buttons (`decorations: false`); macOS (`tauri.macos.conf.json`) and Linux (`tauri.linux.conf.json`) use the system's native title bar, and `TitleBar.svelte` shows window buttons only on Windows.
- Settings `playerHover`: the player bar floats over the bottom edge and shows on hover (`PlayerBar.svelte`).

## Bundled Quran data (works with no connection)
- `app/scripts/bundle-data.mjs` (`npm run bundle`) downloads the surah list, the Arabic text of all 114 surahs (default translation Saheeh) with
  Tajweed markup and IndoPak spelling, and the 604 page fonts into `app/static/data/` and `app/static/fonts/qcf/` (about 120 MB, gitignored,
  so every checkout and CI run must run it: `release.yml` does). The installer carries them; `api.ts` and `fonts.svelte.ts` read them first
  and only go online for other translations and audio (audio is never bundled; the Audio manager downloads it).
- `datasync.svelte.ts`: a weekly background check (25 s after start, online only) compares the provider's text, IndoPak spelling and page-font sizes (`data/manifest.json`, written by the bundle script) with what the app has, and keeps changes in IndexedDB (`<surah>:fresh`, `fonts`, `quran.fresh.fonts`), read before the bundled copy. Changes must pass `sound()` (no verse or word lost).
- Word meanings follow the translation's language (`languages.ts`, `api.extrasOf`); the bundled words are English. Cached text keys end in `:2`.
- First run (`settings.firstRun`): `Welcome.svelte` (theme, size, mode, script, language, word meanings; Skip on every step; flag `quran.welcomed`).
- App icon master is `app/src-tauri/icon-source.png` (`npx tauri icon src-tauri/icon-source.png`, then delete the generated `icons/android` and `icons/ios`). It is the green icon with the gold calligraphy; the golden squircle version (commit `67c2209`) was set aside at the owner's request.
- Run `npm run bundle` once before a local build or dev session; a build without the files still works but fetches from the network.

## Build the Windows installer (only when asked)
WSL2 with Windows interop. Build happens in `C:\Users\magnum\quran-build` (copy of `app/`):
1. `rsync -a --delete --exclude node_modules --exclude .svelte-kit --exclude build --exclude target app/ /mnt/c/Users/magnum/quran-build/`
2. `echo '{"bundle":{"createUpdaterArtifacts":false}}' > /mnt/c/Users/magnum/quran-build/src-tauri/tauri.local.json`
3. `powershell.exe -NoProfile -Command 'cd C:\Users\magnum\quran-build; $env:Path += ";C:\Program Files\nodejs;$env:USERPROFILE\.cargo\bin"; $env:CARGO_PROFILE_RELEASE_LTO="false"; $env:CARGO_PROFILE_RELEASE_CODEGEN_UNITS="16"; npm.cmd run tauri build -- --config src-tauri\tauri.local.json'`
   (the two `CARGO_PROFILE_RELEASE_*` variables are for local builds only, at the owner's request: `Cargo.toml` has `lto = true` and `codegen-units = 1`, which makes the last step single-threaded and slow; CI keeps those. The first build with them recompiles all dependencies, later ones are fast. Keep them the same on every local build or the cache is lost.)
   (run in background, ~5+ min; PowerShell reports exit 1 from stderr even on success).
4. Installer: `quran-build\src-tauri\target\release\bundle\nsis\Quran_<version>_x64-setup.exe`.
   (Tauri 2 signs with env `TAURI_SIGNING_PRIVATE_KEY`, content or path, not `_PATH`. To sign a finished exe: `npx tauri signer sign -f ~/.tauri/quran-desktop.key -p "" <exe>`.)
   Copy to `D:\Downloads\Quran-Beta\` (`/mnt/d/Downloads/Quran-Beta/`) with a README.txt.
Replacing an installer on an existing release (only when asked): upload the exe and its `.sig` with `gh release upload --clobber` and put the new signature in `latest.json`. The copy can fail with "Permission denied" if an installer is running; don't kill the owner's process. Don't install on the owner's PC unless asked. Don't use `-ExecutionPolicy Bypass`.

## Releases and updates
- `.github/workflows/release.yml`: pushing a `v*` tag builds Windows (.exe) + macOS (.dmg) + Linux (.AppImage, .deb, .rpm on ubuntu-22.04), signs update
  artifacts, publishes `latest.json`. Releases are normal (non-pre-release) even for `-beta` tags, so the updater sees them; notes come from `.github/release-notes/<tag>.md` + `footer.md`.
- Needs secrets `TAURI_SIGNING_PRIVATE_KEY` (+ `_PASSWORD`, empty). Key is `~/.tauri/quran-desktop.key`;
  the public key is in `app/src-tauri/tauri.conf.json`. Losing the key breaks updates for installs.
- Installed apps only see updates from a public repo's non-prerelease `latest`.
- Update flow (`updater.svelte.ts`, toast in `+page.svelte`): 4 s after launch and every 2 h, `check()` finds a newer signed release and downloads it quietly; a failed check is retried after 10 min (up to 4 times). A toast in the bottom-left corner says "Version X is ready" with one button, Restart to update (`install()` then `relaunch()`; if the installer fails the state becomes `error` and the next check starts over). Closing the window with an update waiting installs it instead of hiding to the tray. Checked: the pubkey in `tauri.conf.json` is the one in `~/.tauri/quran-desktop.key.pub` and the signatures in the live `latest.json` carry the same key id (FE5C80623DE32C7C). Not covered: tray "Quit" does not apply a waiting update; rpm installs match the generic `linux-x86_64` (AppImage) entry in `latest.json` and cannot update themselves.
- Uninstaller (`src-tauri/windows/hooks.nsi`) removes app data unless `$UpdateMode`; verified earlier. The same hooks file defines `MUI_UNICON` so the uninstaller shows the Quran icon (hooks are included before Tauri's `UNINSTALLERICON` check).
- Linux AppImage audio: without GStreamer plugins inside it, pressing play froze the UI on Fedora. `bundle.linux.appimage.bundleMediaFramework` is on and the CI job installs the GStreamer packages (including ugly and libav for MP3). The CI step deletes `libgstwebrtc.so` before bundling: it links libsoup 2, and WebKit (libsoup 3) aborts the web process ("libsoup3 symbols detected"), which showed as "Could not load this surah" in the AppImage. Found by running the extracted AppImage under WSLg (`--appimage-extract`, then `AppRun`). Unverified on Fedora until tested.
- rpm: RPM versions cannot contain a hyphen, so `rpm` is not in `bundle.targets`; the last step of the Linux job builds it separately (`tauri build --bundles rpm` with the version split into version `0.0.5` and release `0.beta.1`) and uploads it with `gh release upload`. It is not in `latest.json` (no in-app updates for rpm or deb).
- Workflow actions are pinned to commit hashes (comment shows the tag); to update one, look up the new hash with `gh api repos/<owner>/<repo>/commits/<tag> --jq .sha`. The tag is passed to the version step as the `TAG` env var, never pasted into script text. `dtolnay/rust-toolchain` needs `toolchain: stable` because pinning removes the `@stable` hint.
- App CSP (`app.security.csp` in `tauri.conf.json`): scripts only from the app itself (Tauri adds hashes for the SvelteKit bootstrap script), no objects, frames or form posts. `connect-src` and `media-src` allow any `https:` because audio and its offline download come from hosts the quran.com API names (so they cannot be listed); images only from static.qurancdn.com. Tested against the production build in Chromium with no violations; not yet seen in a real Tauri window. If something silently stops working in the installed app (audio, fonts, portraits, updates), suspect this first.
- Faster CI: betas (a hyphen in the tag) build with `CARGO_PROFILE_RELEASE_LTO=false` and 16 codegen units (stable tags keep `lto = true`, 1 unit). The Rust cache is saved only by runs on `main` (a tag's cache is not readable by the next tag), so start releases with `gh workflow run release.yml --ref main -f tag=vX.Y.Z` (add `-f only=windows|macos|linux` for one platform); the first run on `main` per platform is cold, later ones are warm. A tag push still works but only restores.
- Moving a release: delete it with `gh release delete <tag> --cleanup-tag -y`, make sure the tag is gone locally and on the remote (`git push origin :refs/tags/<tag>`), then tag the new commit and push the tag. Cancel a running build first (`gh run cancel`).
- Version lives in `app/package.json`, `app/src-tauri/tauri.conf.json`, `app/src-tauri/Cargo.toml`
  (CI overrides from the tag).
